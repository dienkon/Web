## 2. Root-Cause Findings & Implemented Changes

### 2.1. Root Cause of Realtime Chat Jitter ("dựt dựt, nhảy phiên hoài")
- **Finding 1 — Ephemeral Serverless RAM Split-Brain**: On Vercel Serverless (`api/*.ts`), `liveChatByEvent = new Map()` lived inside per-container RAM. Consecutive `GET /api/minigames/:id/chat` polls every 2.2s landed on different warm/cold Lambda instances, returning completely different message subsets or empty arrays (`[]`) — causing visible "session jumping".
- **Finding 2 — Client RTDB Optimistic Write Rollback**: When `database.rules.json` was not yet deployed via Firebase CLI, client `set(push(ref(rtdb, ...)))` fired a local `onValue` optimistic event and then rolled back on `PERMISSION_DENIED` with `snap.val() === null`, overwriting React state with `[]` before the next API poll restored messages.
- **Finding 3 — Fragmented Per-Event Rooms**: Navigating between Lobby, Solo Games, and individual Event IDs switched `eventId` keys, breaking conversation continuity.
- **Fix Implemented**:
  - Added `getAdminRtdb()` in `server/firebaseAdmin.ts` (`firebase-admin/database` `getDatabaseWithUrl`) so all Vercel Serverless instances read/write one shared RTDB path (`minigame_chat/global` and `minigame_cheers/global`) using Admin credentials (with `1.2s` in-process cache and Firestore `minigame_chat_rooms` fallback if RTDB URL is absent).
  - Rebuilt client chat multiplexing in `src/services/minigameClientService.ts` (`RoomChatController` + `mergeChatMessagesMonotonically` + `sessionStorage` hydration + deterministic client `id` + signature-gated listener notifications) and smart scroll pinning in `src/components/minigame/MinigameRealtimeChat.tsx`.

### 2.2. 4 New Live Welfare Games & 5 Free Solo Games
- Extended `src/types/minigame.ts`, `src/services/minigame/gameLogic.ts`, `src/services/minigame/minigameAssets.ts`, `server/services/minigameService.ts`, `server/routes/minigameStudentRoutes.ts`, `RaceTrackStage.tsx`, `PlinkoDropStage.tsx`, `PenaltyShootoutStage.tsx`, `ClawMachineStage.tsx`, `SoloMinigameArcade.tsx`, `StudentMinigame.tsx`, and `MinigameManagement.tsx`.

## 3. Firestore Read/Write Budget

- **Unified Minigame Chat & Cheers (`minigame_chat/global`, `minigame_cheers/global`)**:
  - Primary storage uses **Firebase Admin Realtime Database (`getAdminRtdb()`)** + `1.2s` server RAM cache → **`0` Firestore reads and `0` Firestore writes** during normal production operation.
  - Fallback doc `minigame_chat_rooms/{roomKey}` is touched **only** if `FIREBASE_DATABASE_URL` / Admin RTDB is unavailable.
- **Free 24/7 Solo Arcade (`SoloMinigameArcade.tsx`)**:
  - Runs 100% client-side with `localStorage` personal high-score persistence → **`0` Firestore reads and `0` Firestore writes**.
- **Live Minigame Events**:
  - Unchanged single-document event model (`minigame_events/{eventId}`), maintaining minimal read budget.

## 4. Security Boundaries

- **100% Free Welfare & Solo Entertainment (`0đ`)**:
  - Neither the 12 Live Welfare Minigames nor the 5 Solo Arcade games deduct wallet balance, charge fees, or accept paid wagers.
  - Solo Arcade scores are strictly honor/leaderboard entertainment (`0đ`) and cannot mint wallet VND or vouchers; wallet prize distribution remains exclusively Admin-triggered (`requireAdmin`) on server-verified `minigame_events`.
- **Authenticated & Sanitized Chat**:
  - `POST /api/minigames/:id/chat` and `GET /api/minigames/:id/chat` require `verifyFirebaseToken`.
  - Server strips control characters, enforces 280-char message cap, bounds `roomTag` to 48 chars, verifies Admin role from `users/{uid}` / custom claims (never trusting client `isAdmin`), and caps stored history to 60 messages (24h TTL).
- **Firestore Rules (`firestore.rules`)**:
  - Added `match /minigame_chat_rooms/{roomId}` with `allow read: if isAuthenticated(); allow write: if isAdmin();` — no client write weakening.

## 7. Remaining Risks

- **RTDB Regional Latency (~40–120ms)**: Cold Vercel Serverless invocations initialize the Admin RTDB connection on first chat request; the `1.2s` RAM cache and client optimistic rendering (`pending: true` with stable `id`) mask any cold-start latency from the user.
- **High-Concurrency Chat Trimming**: When >60 messages accumulate in `minigame_chat/global`, server-side pruning removes the oldest keys asynchronously; monotonic client merging caps local state to the latest 60 messages (`24h` TTL) so memory stays bounded.
